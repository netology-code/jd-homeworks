# Домашнее задание к занятию «8.6. Безопасность в веб-приложениях, Spring Security»

### Цели задания

Это задание поможет вам настроить безопасность в веб-приложении на Spring Boot с использованием Spring Security.

Безопасность — обязательная часть работы backend-разработчика. Приложение, которое выходит в продакшн, должно защищать данные пользователей. В актуальных версиях Spring Boot 3 для этого используется конфигурация через SecurityFilterChain.

В этом задании вы внедрите Spring Security и настроите доступ к эндпоинтам в зависимости от роли пользователя.

**Выполнив это задание, вы:**
*   **научитесь настраивать безопасность без использования устаревшего наследования** — через декларативную конфигурацию (так пишут код в актуальных версиях Spring Boot 3);
*   **освоите работу с паролями** — перестанете хранить их в открытом виде и начнёте использовать хеширование BCrypt;
*   **разовьёте навык отладки конфигурации** — сможете самостоятельно проверять сценарии доступа и находить ошибки в правилах авторизации;
*   **соберёте портфолио-решение** — гготовый модуль безопасности, который можно использовать как шпаргалку в будущих проектах.

# ОПИСАНИЕ ЗАДАНИЯ

## Проект: «Защищённая библиотека»

### Легенда / Контекст

Вы — Java-разработчик в команде, которая создаёт внутренний сервис для библиотеки.
Минимальная версия продукта уже готова: есть работающее CRUD-приложение для книг. Но сейчас служба поддержки прислала **требование**: данные должны быть защищены.

**Проблема:** любой пользователь может зайти на сайт и удалить книги, потому что нет авторизации.

**Ваша задача:** внедрить Spring Security так, чтобы:
- список книг видели все (публичная витрина);
- просмотр деталей книги — только для зарегистрированных читателей;
- добавление и удаление книг — только для сотрудников библиотеки (администраторов);
- пароли администраторов и читателей нельзя получить из базы.

**Требование от технического руководителя:** «Мы переходим на Spring Boot 3. Используйте только современную конфигурацию: `SecurityFilterChain`. Не используйте `WebSecurityConfigurerAdapter` — он устарел. Пароли хешируем с помощью BCrypt».

## Что нужно сделать (Техническое задание)

### Часть 1. Подготовка (стартовый проект) 

У вас есть два варианта:
1. **(рекомендуемый)** взять готовый проект с предыдущих занятий (например, про Hibernate или JDBC), где есть сущность Book и контроллер с методами;
2. создать минимальное приложение с нуля.

**Требования к стартовому проекту:**
- наличие Spring Boot Starter Web;
- контроллер с минимум **тремя эндпоинтами** (например, `GET /books`, `GET /books/{id}`, `POST /books`).
- при запуске приложение работает, эндпоинты отвечают (пока без безопасности).

---

### Часть 2. Внедрение безопасности (Ваша основная задача)

**Шаг 1. Подключите зависимость**
Добавьте в `pom.xml`:
```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
</dependency>
```
*Запустите приложение. Убедитесь, что все эндпоинты теперь защищены (выдаётся форма логина).*

**Шаг 2. Создайте конфигурационный класс**
Создайте пакет `config`, внутри класс `SecurityConfig`.
**Запрещено** наследоваться от `WebSecurityConfigurerAdapter`.
**Разрешено** объявлять бины `SecurityFilterChain`, `UserDetailsService`, `PasswordEncoder`.

**Шаг 3. Настройте правила доступа**
Реализуйте бин `SecurityFilterChain` со следующими правилами:

| Эндпоинт | Метод | Кто имеет доступ |
|----------|-------|------------------|
| `/books` | `GET` | **Все** (permitAll) |
| `/books/{id}` | `GET` | Только аутентифицированные пользователи (authenticated) |
| `/books` | `POST` | Только пользователи с ролью `ADMIN` |
| `/books/{id}` | `DELETE` | Только пользователи с ролью `ADMIN` |
| Любой другой эндпоинт | Любой | Только аутентифицированные |

**Обязательно:** Включите `formLogin(Customizer.withDefaults())` для входа через стандартную форму Spring Security.

**Шаг 4. Настройте пользователей и шифрование паролей**
- Создайте бин `PasswordEncoder` типа `BCryptPasswordEncoder`.
- Создайте бин `UserDetailsService` (реализация `InMemoryUserDetailsManager`).
- Заведите **двух пользователей**:
  - `user` с паролем `p@ssw0rd` и ролью `USER`.
  - `admin` с паролем `admin123` и ролью `ADMIN` (а также `USER`, если требуется).
- **Важно:** Пароли должны быть закодированы через созданный `PasswordEncoder`. Никаких `{noop}`.

**Шаг 5. Проверка работоспособности**
Самостоятельно протестируйте приложение, используя браузер или Postman.

**Чек-лист для самопроверки:**
1. Запустите приложение, перейдите на `http://localhost:8080/books`. Страница должна открыться **без запроса логина**.
2. Перейдите на `http://localhost:8080/books/1`. Должен произойти **редирект на `/login`**.
3. Войдите под учётной записью `user/p@ssw0rd`. После входа страница `/books/1` должна открыться.
4. Выйдите из системы (`/logout`), зайдите под `admin/admin123`. Попробуйте отправить `POST` запрос на `/books` (например, через Postman или форму). Должен быть **успех (200/201)**.
5. Выйдите, зайдите под `user`. Попробуйте тот же `POST /books`. Должна быть **ошибка 403 Forbidden**.

### Часть 3. Документирование

Создайте в корне вашего репозитория файл **`README-SECURITY.md`**.
В нём кратко опишите:

1. **Какие эндпоинты открыты**, а какие защищены (табличка, аналогичная той, что в Шаге 3).
2. **Где хранятся пользователи** (InMemory) и как кодируются пароли (BCrypt).
3. **Какие роли существуют** и какие у них права.
4. **Инструкцию по запуску и проверке** — буквально 3-4 шага.

*Этот файл симулирует техническую документацию, которую вы пишете для команды или заказчика.*

# КРИТЕРИИ ОЦЕНКИ ЗАДАНИЯ

Работа будет проверяться экспертом по следующим критериям.

**«Зачёт» ставится, если:**

1. **Актуальность API:** Конфигурация выполнена **исключительно** через `@Bean SecurityFilterChain`. Класс не наследует `WebSecurityConfigurerAdapter`. *(Соответствует слайдам 24-26 презентации)*.
2. **Правила доступа:** Настроены корректно:
   - Публичный эндпоинт (например, `GET /books`) открыт без авторизации.
   - Остальные эндпоинты требуют аутентификации.
   - Административные эндпоинты защищены ролью `ADMIN` (проверка через `hasRole`).
3. **Аутентификация:**
   - Включена стандартная форма логина (`formLogin`).
   - Пользователи созданы в памяти.
   - **Пароли закодированы** с помощью `BCryptPasswordEncoder`. Отсутствует префикс `{noop}`.
4. **Работоспособность:** При компиляции и запуске нет ошибок. Сценарии «гость/авторизованный/админ» отрабатывают согласно ожиданиям (коды 200, 302, 403).
5. **Документация:** В репозитории присутствует файл `README-SECURITY.md`, описывающий конфигурацию безопасности, роли и эндпоинты.

**«На доработку» ставится, если:**

- Используется устаревший `WebSecurityConfigurerAdapter` (работа не принимается, требуется полная переработка).
- Пароли хранятся в открытом виде (`{noop}`) или не используется `PasswordEncoder`.
- Не работает один из ключевых сценариев (например, администратор не может создать книгу).
- Отсутствует документация.
- Работа сдана с ошибками компиляции.

**«Незачёт»** ставится в крайнем случае, если работа не соответствует заданию, сдана не в том формате или после 2-й итерации доработок не исправлены критические замечания.
